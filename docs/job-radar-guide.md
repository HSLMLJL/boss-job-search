# Job Radar 使用指南

Job Radar 把一次找工作拆成一个可以复用的任务：先说明你想找什么，再决定采集深度和预算，最后在同一个本地工作区里比较、标记和导出。它适合持续找工作，而不是只保存一张容易过期的表格。关键词、城市和规则由你决定，适用于不同城市、行业和岗位方向，不局限于 AI 产品经理。

## 先用界面，再用配置文件

日常使用优先用界面，不需要写 JSON。安装依赖后可先启动工作台并点击“体验合成示例”；它不需要 Chrome 扩展、BOSS 登录或模型密钥。Windows 新手安装步骤见 [快速开始](job-radar-quickstart.md)。

```bash
uv sync
uv run python -m job_radar ui
```

准备真实搜索时，再完成一次 Chrome Bridge 设置：

```bash
uv sync
uv run python -m job_radar setup
```

`setup` 会启动本地 Bridge 并打印本仓库 `extension` 文件夹的绝对路径。在日常 Chrome 打开 `chrome://extensions`，开启开发者模式，选择“加载已解压的扩展程序”，选择该目录；随后在这个 Chrome 中登录 BOSS 直聘。无需复制 Cookie，也不需要运行 `boss login`。Chrome 自己维护登录状态。

之后日常使用：

```bash
uv run python -m job_radar ui
```

浏览器打开本机界面后，新建任务或从模板开始。配置文件适合想保存、复制或版本管理搜索条件的用户：

```bash
uv run python -m job_radar init --output my-search.json
uv run python -m job_radar run my-search.json
```

`init` 生成的文件是完整起点。配置只接受下文列出的字段；城市和枚举筛选值必须是界面/程序提供的可选值。

## 一份任务配置由什么构成

```json
{
  "name": "我的产品岗位搜索",
  "keywords": ["产品经理", "增长产品"],
  "cities": ["上海", "杭州"],
  "details": "matched",
  "filters": {},
  "limits": {},
  "export": {}
}
```

### 搜索：关键词和城市

`keywords` 和 `cities` 都是列表，至少各填一项。多个关键词并不是“岗位标题必须同时包含所有词”：系统会分别搜索，再把结果汇到同一次任务中。因此建议把同义叫法、相近职位和你愿意考虑的方向分开写，例如：

```json
"keywords": ["产品经理", "增长产品", "用户研究"]
```

每条岗位会保留 `queries`，告诉你它命中了哪些搜索词；同一岗位在多次搜索里出现时不会在导出中变成多条独立岗位。

### 采集完整 JD：三个选择

`details` 控制是否访问岗位详情页并记录完整 JD：

| 值 | 含义 | 适合什么情况 |
| --- | --- | --- |
| `none` | 只收集列表信息 | 第一次宽搜、快速查看市场 |
| `matched` | 只为本地筛选规则通过的岗位补全 JD | 日常找工作，兼顾速度和判断信息 |
| `all` | 为本次所有收录岗位尝试补全 JD | 关键词和城市范围较小、需要做市场研究 |

完整 JD 不是必需项。`matched` 不是 AI 匹配评分，只表示岗位通过了你自己设置的本地规则。先跑 `none` 或 `matched`，确认范围后再提高深度，通常更容易控制时间和结果质量。详情面板没有正文、达到详情预算或任务中断时，结果会保留 JD 状态，不把它误写为完整 JD。Job Radar 不会据此自动改写简历；如何把 JD 清单用于人工准备投递材料见 [JD 与简历准备](job-radar-resume-workflow.md)。

### 筛选：平台条件与文本条件一起用

`filters` 支持两层筛选。

第一层是岗位页面通常提供的条件：`salary`、`experience`、`education`、`industry`、`scale`、`stage`、`job_type` 和 `welfare`。这些字段的具体可选值由界面显示或由 `init` 生成的配置提示；多个枚举值用英文逗号分隔。当前版本先采集搜索页面的岗位列表及可选 JD，再在本地应用筛选规则；因此不要假设每个配置项都会作为平台页面的搜索参数发送。

第二层是文本条件：

```json
"filters": {
  "include": ["AI", "增长"],
  "exclude": ["电话销售", "直播"],
  "exclude_internships": true,
  "exclude_hourly_daily": true,
  "unknown": "keep"
}
```

- `include`：帮助确认你关心的方向；请使用能解释的具体词，不要把它当作岗位好坏的唯一判断。
- `exclude`：排除明确不考虑的工作内容或方向。
- `exclude_internships` / `exclude_hourly_daily`：按你的求职计划关闭实习、小时工或日结类岗位。
- `unknown`：条件字段缺失时，`keep` 会留给你人工判断，`exclude` 会随筛选排除。刚开始建议用 `keep`，避免因信息不完整错过岗位。

筛选通过与否以及原因会写入导出结果。它是帮助缩小范围的规则，不替代你阅读 JD、确认公司和判断机会。

### 预算：给每次任务一个可解释的边界

```json
"limits": {
  "pages": 5,
  "requests": 50,
  "details": 30,
  "jobs": 300,
  "seconds": 900
}
```

`limits.pages` 按每个“关键词 × 城市”组合分别计算；其余上限由本次启动或继续运行的所有组合共用。共同预算可能在后续组合开始前用尽。达到岗位数上限后，仍可在剩余详情、请求和时长预算内补齐已保存岗位的 JD。上限不是“预期一定拿到多少条岗位”，而是保护本次运行的可控范围。任务页会保存进度和已完成页面。只有专用搜索页仍在、且扩展的页面检查点未丢失时，中断后才可以尝试继续：

```bash
uv run python -m job_radar resume RUN_ID
```

如果任务不是自然完成，先看覆盖范围和完成状态，再决定是否继续。继续时使用新的预算窗口。浏览器或扩展重启会失去页面检查点：已保存的岗位、导出和已完成页面记录仍保留，但任务会明确停止，需要新建搜索，不能承诺跨重启继续。不要把“这次没扫到”理解为“平台没有”。

### 导出：只拿你要用的字段

```json
"export": {
  "formats": ["xlsx", "csv"],
  "fields": ["title", "company", "city", "salary", "description", "url", "status", "notes"],
  "scope": "matched"
}
```

- `formats`：`xlsx`、`csv`、`json` 可任选一种或多种。
- `fields`：可选岗位名称、公司、城市、薪资、经验、学历、福利、技能、完整 JD、链接、JD 状态、筛选依据、命中关键词、首次/最近收录时间、平台发布时间、变化、个人状态和备注。
- `scope`：`matched` 只导出筛选通过岗位；`all` 导出本次全部收录岗位；`new` 导出本地工作区首次收录的岗位，不论它是否通过本次筛选，便于复查筛选规则。

使用命令导出已有任务：

```bash
uv run python -m job_radar export RUN_ID
```

## 历史、去重和个人进度

工作区会为岗位建立稳定标识。同一岗位下次再次出现时，会继承你写过的进度和备注，并更新最近收录时间。结果中的 `change` 通常表示：

- `first_seen`：第一次被这个本地工作区收录；不是平台发布时间。
- `seen`：与此前相比主要信息未变，本次再次看到。
- `changed`：岗位的关键列表信息与此前记录不同，值得人工确认。

你可以使用 `待看`、`考虑`、`已投`、`面试`、`不合适` 管理状态。它们是你的工作记录，不会替你修改 BOSS 上的投递状态。

## 任务模板

如果你会每周找同一类岗位，把已验证的关键词、城市、筛选、JD 策略和导出字段存为模板。模板不是锁死搜索：例如你可以保留一个“产品岗位·华东”模板，再临时加上“北京”或更换关键词。每一次运行仍会独立记录自己的配置和结果。

## 两个实用策略

### 先宽后深

第一步用 `details: none`，城市和关键词可以略宽；看过岗位列表后，再调好 `include`、`exclude` 和平台条件。第二步改为 `details: matched`，只为通过筛选的岗位补全 JD。这样能减少无关详情采集，也能让“为什么保留这条岗位”更清楚。

### 每天优先看新增，不遗忘旧机会

导出范围选 `new`，查看第一次收录的岗位；同时在完整历史中关注已标为 `考虑` 但尚未处理的岗位。这样既不会把重复出现的职位当成新机会，也不会因为当天没有新增而忽略以前值得跟进的岗位。

## 本地数据、Chrome 与运行中的页面

默认工作区在：

```text
~/.boss-agent/job-radar
```

其中保存任务、岗位历史、状态和备注。需要隔离测试数据时，使用：

```bash
uv run python -m job_radar --data-dir PATH run my-search.json
```

`--data-dir` 只隔离任务、岗位历史、状态、备注和导出等本地工作库，不保存或迁移 Chrome 的登录状态。真实采集使用已加载 Bridge 扩展的日常 Chrome；登录完全由 Chrome 维护。请不要分享包含个人备注和导出内容的数据目录。日常安装只需 `uv sync`；参与开发或运行测试时再加 `uv sync --extra dev`。

每次真实搜索会使用扩展绑定的专用 Chrome 搜索标签页。运行时让该页保持可见，不要同时手动修改搜索词、筛选或翻页；这能让列表翻页和职位 ID 验证保持一致。完整 JD 从同页可见的职位详情面板读取，并按职位 ID 核验。面板没有正文、无法支持或运行中断时，JD 会标记为未完成，而不是写成完整采集。

## 搜索没有拿到岗位时

先查看运行状态和已采集数量；有导出文件不代表搜索成功，零条结果也可能是登录、连接或验证问题。

| 运行状态 | 含义 | 下一步 |
| --- | --- | --- |
| `auth_required` | Chrome 页面要求登录，或 Bridge 未连接 | 在日常 Chrome 登录 BOSS；确认扩展已加载并重新打开工作台 |
| `risk_stopped` | 页面要求安全验证，或接口明确返回风险/频率限制 | 暂停自动重试，在网页上人工确认并完成必要验证；恢复正常后再继续 |
| `stopped` / `failed` | 用户停止、连接失败、页面检查点丢失或其他错误 | 阅读该次运行的具体提示，保留已得到的结果；若搜索页或扩展重启，创建新任务而非跨重启继续 |
| `budget_stopped` / `partial` | 本次预算或页面范围已到上限 | 查看实际覆盖范围，再决定是否继续；不要把未访问的范围算作零岗位 |

首次真实测试建议只选一个关键词、一个城市，设置最多 5 个岗位和 3 条 JD，检查岗位链接、正文和导出后再扩大范围。Chrome 已登录并不保证页面始终可用；以本次任务状态和页面提示为准。

## 常见问题

**为什么没有完整 JD？** 先检查 `details` 是否为 `none`；再看 JD 数量上限是否已经达到，以及该岗位是否通过了 `matched` 的筛选规则。列表卡片上的简短描述不等于完整 JD；只有详情请求返回非空内容时，才应视为完成 JD 采集。

**为什么列表里有岗位，导出的“匹配岗位”没有？** 它没有通过你的筛选条件。导出 `all` 并查看“筛选依据”可帮助调整规则。

**为什么“首次收录时间”是今天，岗位却显示更早？** 首次收录只表示你的本地库今天第一次看到它；若页面提供平台发布时间，两者会分开保存。

**可以用来自动投递吗？** 这里的工作区面向搜索、判断、整理和跟进。投递和沟通由你在平台上主动完成。
